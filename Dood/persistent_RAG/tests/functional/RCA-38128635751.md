# RCA: DooD functional CI run 38128635751

Failed job: https://github.com/SergeyIvanov87/Code-Metric-Visualizer-Platform/actions/runs/38128635751/job/114439887263

## Impact and evidence

Both black-box tests failed because the agent filesystem API never accepted their requests. Each query exhausted its 900-second acceptance timeout, adding 30 minutes after the 15-minute controller startup wait. Image build, artifact download/load, and tester build succeeded; failures occurred before embedding downloads or inference.

The diagnostics show `persistent-rag-ai-agent-1` in `Created`, Chroma repeatedly becoming unhealthy, and the controller reporting `dependency failed to start: container persistent-rag-rag-db-1 is unhealthy` before tearing down and recreating its siblings. The dispatcher became healthy, but the agent requires both Chroma and the dispatcher.

## Root cause

The internal Chroma health check invoked `python -c ...` to request `/api/v2/heartbeat`. The exact pinned image, `chromadb/chroma:1.5.9.dev10-amd64`, is a Rust runtime with no Python interpreter. Reproducing the command in that image returns `/bin/sh: 1: python: not found` and exit code 127. Installing openssh-server in the framework RAG Dockerfile does not provide Python. Thus the probe could not run even though Chroma itself started.

This was an implementation error in the new DooD stack: the probe's runtime dependency was assumed instead of checked against the deployed image.

## Contributing factors

The controller exits on dependency failure, cleans up its siblings, and restarts, repeatedly resetting startup. The outer Compose startup command consumed exactly its 900-second wait budget and the CI step was reported successful without any controller-ready evidence. The workflow trusted that return code and ran the tester with `--no-deps`, bypassing its Compose health dependency. Its two queries then spent their full timeout waiting for an agent that had never started.

The original diagnostics collected logs and container summaries but not Docker health-probe output, making the missing executable harder to identify directly.

## Fix and prevention

- Install curl explicitly in the DooD RAG wrapper and probe the actual HTTP heartbeat with failure handling, a five-second timeout, and a localhost proxy bypass.
- Independently inspect the controller and each application sibling for `running/healthy` after Compose's startup wait; reject missing, starting, or unhealthy services before API testing.
- Run the real Chroma heartbeat smoke check in the build job before exporting its controller artifact.
- Record sibling container State, including health-check output and exit codes, before teardown.
- Reproduce the original missing-Python failure, build the actual framework RAG base and wrapper, exercise the fixed production heartbeat against live Chroma, and test readiness rejection when Compose returns success for an unready stack.

Validation passed: both RAG images built, live Chroma became healthy with an HTTP heartbeat and probe exit code 0, unhealthy/missing readiness cases were rejected, Compose validation passed, and actionlint passed.

The complete model-backed suite still requires the next GitHub Actions run; these checks specifically verify this startup failure and the readiness gate.
